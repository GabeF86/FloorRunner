# UI v1: Professionalization + Assistant Expansion — Design Spec

**Date:** 2026-07-10 · **Branch:** `ui-v1` · **Requested by:** Gabriel ("optimize the floor runner application so that it looks and feels more professional and easier to use… then build a chat bot using claude api to help the user run the schedule more efficiently"). Design decisions delegated to Claude; user away for the evening.

## §1 Problem statement (from the 2026-07-10 UI survey)

FloorRunner's backend far outpaces its frontend. Concretely:
- **No design system in practice.** Tailwind installed, used in one file. Everything else is inline `style={{}}` objects. Three competing token conventions: `globals.css` CSS vars (the only coherent layer, real dark+light themes), `schedules/[id]/gridTheme.ts` (hardcoded hex + tested `cellBackground()`), and staffing-calculator's local `tok` object.
- **Two disjoint shells.** `(scheduling)/layout.tsx` provides an 11-item dark sidebar but force-overrides content to light via inline vars; `/board` lives outside the group with its own sidebar and its own theme toggle. Same app, two looks.
- **Near-zero reuse.** One shared component (`ShiftTypePicker`). Modals re-implemented in 13 files, pill badges in 13, 217 raw inline-styled buttons, 11 hand-styled tables.
- **Stub first impressions.** `/dashboard` (the landing redirect target) shows four hardcoded `'—'` cards; `/reports` is a "coming soon" line.
- **Uneven states.** Loading/error/empty handling is ad-hoc or absent (no `loading.tsx`/`error.tsx` anywhere); desktop-only fixed-pixel layouts; thin ARIA.
- **The assistant is schedule-page-only.** Its chat plumbing (SSE reader, streaming bubbles, undo chips) is generic except three seams (endpoint, `onMutated`, copy), and it has no read/analysis tools — it can change schedules but can't answer questions about them.

## §2 Goals / non-goals

**Goals**
1. One design language: a single token layer + a small shared component library, adopted by every screen.
2. One shell: unified nav + theme across scheduling pages and the board.
3. A real dashboard: live numbers, today-at-a-glance, entry points.
4. Consistent loading/empty/error states on every data page.
5. Assistant that helps *run* the schedule: read/analysis tools (coverage, fairness, unfilled, who's-on), efficiency guidance in the prompt, reachable beyond the single grid page.

**Non-goals (deliberate)**
- No rewrite of the 1,700–2,800-line page monoliths (`providers/[id]`, `schedules/[id]`, `staffing-calculator`). They get chrome/consistency passes only; extraction is future work.
- No Tailwind migration. The CSS-var + inline-style idiom is entrenched and works; we systematize it instead of replacing it (removing Tailwind is also out of scope — it stays for the one file using it).
- No mobile layouts. Desktop-first internal tool; we only avoid making responsiveness worse.
- No new UI dependencies (no Radix/shadcn/framer). The library is small, hand-rolled, matching the existing aesthetic. Zero-dep keeps the build stable and the diff reviewable.
- No auth/RLS (still the roadmap's separately-tracked blocker).
- `/reports` stays a stub (needs product thinking with Gabriel; not an evening deliverable).

## §3 Design language

Keep and extend what already works: **dark-first, DM Sans/DM Mono, CSS variables**. The board's current look (dense, calm, high-contrast accents) is the aesthetic anchor; the staffing calculator's `cardStyle` is the surface treatment high-water mark.

- **Tokens** (all in `globals.css`, both themes): existing `--bg-*/--border-*/--text-*/--blue/--indigo` stay; ADD spacing scale (`--space-1..8`: 4/8/12/16/20/24/32/48px), radius scale (`--radius-sm/md/lg`: 6/10/14px), type scale (`--fs-xs/sm/md/lg/xl`: 11/12.5/14/17/22px), semantic status colors (`--ok/--warn/--danger/--info` + `-bg` soft variants), `--focus-ring`. Every shared component consumes only vars.
- **Component library** `src/components/ui/` (one file per component, inline styles consuming vars): `Button` (primary/secondary/ghost/danger; sm/md), `Card` (+ header/footer slots), `Badge` (status pill), `Modal` (portal, backdrop click + Escape close, focus trap-lite, sizes), `Table` (styled thead/tbody wrapper, empty-state slot), `EmptyState` (icon/title/hint/action), `Skeleton` (line/block shimmer), `PageHeader` (title/subtitle/actions row), `Banner` (info/warn/error/success inline alert), `Spinner`. Named exports from `src/components/ui/index.ts`.
- **Theme**: one source of truth — the existing `data-theme` attribute + localStorage init script in the root layout. The `(scheduling)` layout's forced-light override is removed; both shells honor the toggle, which moves into the shared shell header.

## §4 Unified shell

New `src/components/AppShell.tsx`: the (scheduling) sidebar generalized — sections **Overview** (Dashboard), **Scheduling** (Schedules, Providers, Sites, Rules, Requests), **Staffing** (Staffing Calculator, Grid Calculator), **Operations** (Floor Runner board), **Admin** (Settings), plus a footer theme toggle. `(scheduling)/layout.tsx` becomes a thin wrapper around AppShell. `/board` gets a `board/layout.tsx` using AppShell with a `fullBleed` content mode; `BoardClient`'s own nav/theme chrome is removed (its localStorage board prefs stay). The board remains functionally identical — drag-and-drop, plan mode, supervision alerts untouched.

## §5 Dashboard

Server component + `loading.tsx` skeleton. Data (existing tables only, service client):
- Stat cards: active providers, sites, schedules in progress/published (by status), pending requests (`provider_availability` where `approval_status='pending'`).
- "Today" panel: today's call assignments across published/active schedule versions (provider, site, shift code) — the "who's on call right now" glance.
- Attention panel: per active schedule — unfilled slot count and hard-violation count from stored `validation_flags` summaries; links into each schedule.
- Quick actions: New schedule, Enter requests, Open board.
Empty DB shows EmptyStates with onboarding hints, never dashes.

## §6 Adoption passes (chrome, not rewrites)

- **Pass A (list/admin pages):** providers, sites, schedules, rules, requests, settings → PageHeader + Table + Badge + Button + Modal + EmptyState + Skeleton; local modal implementations deleted.
- **Pass B (detail pages):** `schedules/[id]` chrome (header/toolbar/status toasts→Banner/side panels) with the grid cell renderer and `gridTheme.ts` untouched; `sites/[id]`, `rules/[id]` same treatment; staffing-calculator's local `tok`/`cardStyle` remapped to global vars (visual parity, its layout kept).
- **Pass C (board):** shared Modal for its 3 modal files, tokens for hardcoded hexes, StatsBar/FloatBar/Sidebar spacing+type normalization. Print views untouched.

## §7 Assistant expansion

- **Generalize the chat UI:** extract `src/components/chat/useSSEChat.ts` (fetch-POST SSE reader → event callbacks; the exact protocol AssistantPanel already speaks) and `src/components/chat/ChatDrawer.tsx` (drawer shell: messages, streaming, status/error/notice, composer, image attach, change chips + undo). `AssistantPanel.tsx` becomes a thin wrapper (endpoint + copy + onMutated). No protocol changes.
- **New read/analysis tools** (all read-only, NOT in `MUTATING_TOOLS`, executors reuse engine modules):
  - `get_coverage_summary` — per date-range: filled/unfilled by shift code and date, gaps list. Wraps the grid data the page already loads.
  - `get_fairness_report` — per-provider call counts by bucket vs FTE-scaled expectation (reuses `historical_call_counts` shape + live version counts), stdev, burnout pairs (reuses `metrics.ts` helpers on a reconstructed plan).
  - `find_unfilled` — unfilled slots with per-slot top candidate blockers (mirrors generate-route trimming).
  - `who_is_on` — assignments for a provider or date (+±window), cross-version aware.
- **Prompt:** new "Helping the scheduler run the week" section — proactive-efficiency guidance (surface unfilled/violations first, suggest concrete swaps by naming eligible providers, always quantify fairness claims from tools, never guess when a tool can answer).
- **Reach:** assistant drawer added to the schedules LIST page with a schedule selector (targets one schedule per conversation — the existing backend contract), so questions don't require opening the grid first. Dashboard links to it. (True app-wide/board assistant = future work; keeps this evening's scope honest.)

## §8 Quality bars

Every task: `npm test` green (425 baseline + new), `npx tsc --noEmit` clean, `npm run build` green. Component behavior (Modal close paths, useSSEChat event parsing, dashboard aggregation, new tools) gets vitest coverage with the established fake-supabase/fake-client fixtures; pure-visual components are exercised via build + usage. Reviews per subagent-driven-development (combined reviewer allowed for small diffs). LLM rules from CLAUDE.md hold (fake clients, never network). Clinical invariants are untouched by design — no engine files change except additive read-only tool executors.

## §9 Rollout

Single branch `ui-v1`, task-by-task commits, merge to main after final review. No DB migrations needed (dashboard + tools read existing tables). patch18 remains pending manual application — the assistant features (existing and new) require it on the live DB; the new read tools must degrade with the same warning pattern as the engine when `call_patterns` is absent.
