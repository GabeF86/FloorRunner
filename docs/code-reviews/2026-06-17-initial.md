## [CRITICAL] RLS enabled on all three new tables with ZERO policies → all anon/auth queries fail closed

**File:** `supabase_scheduling_patch14_grid_calculator.sql:111-112`, `supabase_scheduling_patch16_fte_runs.sql:56`
**Category:** security
**Issue:** Patch 14 and patch 16 run `ALTER TABLE … ENABLE ROW LEVEL SECURITY` but ship **no** `CREATE POLICY` statements. With RLS on and no policy, Postgres blocks every SELECT/INSERT/UPDATE/DELETE for non-superuser roles. The existing FloorRunner `scheduling.*` tables follow an `org_access` policy keyed on `organization_id = scheduling.current_user_org_id()` (see `supabase_scheduling_schema.sql:475+`). Neither `grid_calculator_configs` nor `grid_calculator_fte_runs` has an `organization_id` column, so a future `org_access` policy cannot even be retrofitted without another schema change. Patch 15 doesn't touch RLS on `provider_employment_profiles`, but the new columns inherit the existing policy fine (good).

**Why this is CRITICAL:** as soon as the UI tries to read configs (the `/grid-calculator` route hits a Supabase client with the anon/auth role), every query returns 0 rows with no error. Worse, when policies eventually land, the `created_by uuid` column is the only available scoping handle — that's a per-user policy, not the org-scoped policy the rest of the schema uses, which means two providers in the same group can't share a config without bespoke logic. The "policy bodies deferred to a follow-up patch" comment in patch 14 is not a viable plan: the tables must either (a) add `organization_id uuid NOT NULL` columns now and ship the `org_access` policy alongside patch 14, OR (b) ship explicit `FOR ALL TO authenticated USING (true)` development policies and a clear deprecation marker so production deploys don't accidentally inherit "all-access-to-everyone".

**Suggested fix:** Add an `organization_id uuid NOT NULL REFERENCES scheduling.organizations(id) ON DELETE CASCADE` column to both `grid_calculator_configs` and `grid_calculator_fte_runs`, plus an `org_access` policy on each table (mirror `scheduling.sites`/`scheduling.schedules` policies in the schema). `grid_calculator_distances` derives org via `config_id`, same pattern as `provider_employment_profiles → providers → organization_id`.

## Findings

### [ERROR] `fteSimulator.runOneTrial` double-counts solver violations into `peakMDs`/`peakCRNAs` per violation (not per day), inflating Monte Carlo p95 upward

**File:** `src/lib/gridCalculator/fteSimulator.ts:856-859`
**Category:** correctness
**Issue:** Inside the per-weekday loop, after the solver returns, the code does `for (const v of grid.violations) { if (...) peakMDs += 1; if (...) peakCRNAs += 1; }`. A single bad day with N violations bumps the peak by N, not by 1. Worse, these increments are NEVER decremented — they accumulate across days, so once a bad early-year day inflates peakMDs by, say, 8, every subsequent day's `if (used.mds > peakMDs)` check has to clear that inflated bar. The result is a permanently-biased peak feeding the p95 percentile. With the worst-case knobs (15% CRNA call-out + 8% MD call-out + forced PTOs), most days surface 1-2 violations even on adequately-staffed rosters, so this bias is meaningful and consistent across trials.

**Suggested fix:** Track per-day shortage as `Math.max(peakMDs, used.mds + shortMDsThisDay)` where `shortMDsThisDay` is computed once per day from the unique violation set, not by `+=` accumulation across iterations.

### [ERROR] `callBurden.distributeCall` pins providers with `backup_call_eligible: false` if they have a non-null `backup_call_share_target`

**File:** `src/lib/gridCalculator/callBurden.ts:313-321`
**Category:** correctness
**Issue:** The pinned-share loop iterates `roster` (all providers), not `backupPool` (the subset with `backup_call_eligible && fte > 0`). A roster row with `backup_call_eligible: false` and an explicit `backup_call_share_target: 0.3` lands in `backupByProvider` with share 0.3, despite being explicitly ineligible. Because the leave-profile is keyed by provider id (not roster row), this happens silently — there's no warning that the eligibility flag was bypassed.

**Suggested fix:** Skip pinning when `!r.backup_call_eligible`, OR raise a violation (`'Pinned target on backup-ineligible provider — pin ignored'`) so the directors see the conflict.

### [ERROR] `fteSimulator.runWorstCase` returns `unsolvableDays` from only the LAST loop iteration, hiding shortages from earlier growth attempts

**File:** `src/lib/gridCalculator/fteSimulator.ts:509-584`
**Category:** correctness
**Issue:** `unsolvable` is initialized at line 533 INSIDE the outer `while (loops < MAX_LOOPS)` loop, so each grow-and-retry iteration resets the day count to 0. The function returns `unsolvableDays: unsolvable` (line 582), which is the count from whichever pass exited the loop. If the worst-case loop hits the `RECOMMENDATION_MAX` cap (line 519-522), the returned `unsolvableDays` is from the LAST attempted growth, not the maximum or any aggregate. Callers (and the templated rationale at line 1128) treat this number as the "yearly unsolvable count for the recommended roster" — but if the cap fired, it's nothing of the sort.

**Suggested fix:** Either return the day count for the FINAL accepted roster (run one more solve pass with the final headcount), OR rename the field to `unsolvableDaysInLastAttempt` and document the semantics.

### [ERROR] `solver.ts` declares `SupervisorState` interface twice — once inside `solve()` body, once at module scope

**File:** `src/lib/gridCalculator/solver.ts:114-118` and `379-383`
**Category:** type-safety
**Issue:** The local `interface SupervisorState` at line 114 inside `solve()` is shadowed by the module-scope `interface SupervisorState` at line 379. TypeScript happily accepts identical declarations in different scopes, so this compiles, but the local one is dead code (it's never referenced as a type annotation; the array literal at line 119 infers from contents). If anyone refactors and adds a field to one but not the other, the silent divergence will surface as a type error far from the cause. Code smell that escaped TS's "duplicate identifier" check only because the local one happens to be unreferenced.

**Suggested fix:** Delete the local declaration (line 114-118). The module-scope one is the only one used.

### [ERROR] `supervisability.ts` makes `near` BLOCKED-by-default, contradicting `distanceMatrix.ts`'s `defaultBandSupervisability('near') === true`

**File:** `src/lib/gridCalculator/supervisability.ts:204-230` vs `src/lib/gridCalculator/distanceMatrix.ts:37-43, 119-121`
**Category:** correctness (integration)
**Issue:** `distanceMatrix.ts`'s `BAND_DEFAULTS` maps `near → 'warning'`, and `defaultBandSupervisability('near')` returns `true` (because `'warning' !== 'blocked'`). The solver uses `distanceMatrix.isSupervisable` as its fallback (`SAME_SITE_ONLY_MATRIX` aside) — so a fresh config with no `DistanceEdge` overrides allows `near`-pair supervision. **However**, when the UI wires in `makeSupervisabilityResolver(edges)` (see `state.ts:326`), the resolver's `explain()` at supervisability.ts:204-230 BLOCKS `near` unless an edge with `supervisable: true` is explicitly present OR `allowNearOverride` is set. The same config produces different supervisability decisions depending on whether the solver is called bare or wrapped by the resolver. This is a real contract drift — Paoli's seed happens to declare every Main-OR ↔ off-site as `near` with `supervisable: true`, so the seed works either way, but a new hospital onboarding via the sidebar without explicitly toggling the per-edge supervisability checkbox will see different grids depending on whether the resolver is in play.

**Suggested fix:** Pick one policy. Recommend: keep `distanceMatrix.ts` as the single source of truth (band → allowed?), and make `supervisability.ts` add structured warnings on top, NOT override the allowed boolean. The current "near requires explicit override" rule is sound clinically but should live in `distanceMatrix.ts`, not silently in a layer above it.

### [ERROR] `fteSimulator.simulate` augments `roster` before calling `recommendFTE` but `worstCase` was computed on the un-augmented input — the worst-case + p95 combination loses internal consistency

**File:** `src/lib/gridCalculator/fteSimulator.ts:1262-1300`
**Category:** correctness
**Issue:** `runWorstCase(input)` is called once (line 1264) before any float-bump iteration. When the bump loop fires, the float-bumped roster is used for the second `runMonteCarlo` call (line 1287) but the `worstCase` result is from the original input. `recommendFTE(worstCase, monteCarlo, augmentedInput)` then combines them. The `binding` field in the output describes "Anesthesiologist=worst_case" with a number derived from the un-bumped roster, while the CRNA p95 reflects the bumped one. The headline numbers are still internally fine (each is independently clamped), but the rationale generator and the audit row will report inconsistent context for the run.

**Suggested fix:** When the float-bump fires, re-run `runWorstCase(augmentedInput)` as well, and report both deltas in the rationale. OR document the asymmetry explicitly in the rationale: "Worst case is computed pre-bump; Monte Carlo is post-bump."

### [ERROR] `Sidebar.tsx` `onAddRoom` prop typed as `(siteId: string) => void` but `page.tsx` passes `() => {}` — silent type mismatch hidden by TS's contravariant function parameter check

**File:** `src/app/(scheduling)/grid-calculator/page.tsx:82-83` vs `src/app/(scheduling)/grid-calculator/Sidebar.tsx:29`
**Category:** type-safety
**Issue:** TypeScript's bivariant-function-parameter behavior under method shorthand (or with `strictFunctionTypes: true` — Next.js default — but still under a permissive context) accepts `() => void` as assignable to `(s: string) => void`. The page-level stub at line 82 discards `siteId`, which is fine semantically (it's a TODO), but if a future agent flips the signature to require a return value or adds a second parameter, the page-level handler silently breaks. Same pattern for `onChangeBand` (page.tsx:85) and `onToggleSupervisable` (page.tsx:88) — all passed as `() => {}` against handlers typed with explicit args.

**Suggested fix:** Type the stubs explicitly to match — `(siteId: string) => { /* TODO(A11) */ }` — so any future signature change surfaces as a compile error rather than a silent runtime miss.

### [ERROR] `solver.ts:144-145` resolves site rules by `site.name` OR `site.id`, but `rulesNormalizer.ts` is contracted to emit `site` as the human-readable name only — silent fallback hides the case where the LLM emits an ID by mistake

**File:** `src/lib/gridCalculator/solver.ts:139-145`, `src/lib/gridCalculator/prompts/normalizer.md:79-83`
**Category:** correctness
**Issue:** The solver's `ruleBySiteKey` map indexes by `rule.site` only, then `ruleBySiteKey.get(site.name) ?? ruleBySiteKey.get(site.id)` resolves by name first, then ID. The normalizer prompt at lines 79-83 says "Use those spellings VERBATIM. … If the guideline mentions a site that is not in the list, put the sentence in `unmapped`." So the LLM is contracted to ONLY emit human-readable names. The fallback-to-`site.id` path silently rescues a contract violation — better to surface the mismatch as a solver `violations` entry so A12's test loop catches the regression.

**Suggested fix:** Either drop the fallback (`ruleBySiteKey.get(site.name)`) or surface a violation when the fallback hits.

### [WARN] `rulesNormalizer.ts:204-211` uses `edges.find` inside `supervisability.ts`'s `explain` despite already having an indexed `idx` map — O(n) lookup in what should be O(1)

**File:** `src/lib/gridCalculator/supervisability.ts:207-211`
**Category:** performance
**Issue:** Inside `explain`'s `band === 'near'` branch, the code calls `edges.find(e => …)` over the raw edges array even though `idx` (the `indexEdges`-built Map) is already in scope. For a hospital with ~10 sites and ~45 distance edges this is negligible, but the function is called from `safetyScore` which is called for every (room × candidateMDSite) pair during the canvas render — so an N×M-edge product on every render. Universal use case is small but worth fixing now.

**Suggested fix:** Use `idx.get(edgeKey(siteAId, siteBId))` instead of `edges.find(...)` — the edge key helper is already exported from `distanceMatrix.ts`.

### [WARN] `fteSimulator.simulate` returns `seed: input.seed ?? NaN` — production callers that don't pass a seed get NaN persisted to `grid_calculator_fte_runs.seed`

**File:** `src/lib/gridCalculator/fteSimulator.ts:1313`
**Category:** correctness / observability
**Issue:** The simulator internally picks a crypto-seeded RNG when `input.seed` is undefined (`createRng(undefined)` at line 396-397 falls through to `cryptoSeed()` at line 459). That crypto seed is the one actually used for the trials. But the returned `FTERunResult.seed = input.seed ?? Number.NaN` reports `NaN` to the persistence layer, so the persisted row CANNOT reproduce the run. PRD §10 requires "deterministic RNG seeded by the caller" for repro — but the simulator silently drops the seed on the floor when it draws one itself.

**Suggested fix:** Capture the crypto-drawn seed from `createRng` (return it from the factory) and propagate to `usedSeed`. Migration patch 16's `seed bigint` column expects a real value.

### [WARN] `fteSimulator.sampleWithoutReplacement` silently returns fewer than `count` indices when its HARD_CAP fires

**File:** `src/lib/gridCalculator/fteSimulator.ts:917-925`
**Category:** correctness
**Issue:** For the small-count path (`count * 4 < n`), the sampler loops up to `count * 50` attempts, then returns whatever it accumulated. For realistic inputs this never trips (uniform draws over ~250 slots converge in O(count) tries), but a future change that increases `count` near `n/4` (where collisions become non-trivial) will produce silently undersized absent-day sets, biasing the trial's peak headcount downward.

**Suggested fix:** When the HARD_CAP fires, fall through to the dense Fisher-Yates path (lines 927-932) rather than returning a truncated set. Or assert(`out.size === count`) so failures surface loudly.

### [WARN] `solver.ts` float allocator (lines 271-285) emits one CRNA float per non-empty site even when the strategy is `emergency_priority` or `break_priority` — A6's `floatStrategy.applyFloatStrategy` is run AFTER and overrides this, but in the wrong order at `fteSimulator` line 862-868 the solver-internal floats are computed FROM `surplus` which already excludes the solver-emitted ones

**File:** `src/lib/gridCalculator/solver.ts:271-285` vs `src/lib/gridCalculator/fteSimulator.ts:862-868`
**Category:** correctness (integration)
**Issue:** The solver emits "placeholder floats" — one CRNA per non-empty site if surplus remains — then A6 ostensibly replaces them via `applyFloatStrategy`. But in `runOneTrial`, `computeSurplus(dayRoster, grid)` (line 892-902) excludes providers already assigned **including the solver-emitted floats** (line 898). When `applyFloatStrategy` then runs on a surplus that's been depleted by the placeholder floats, A6 sees a smaller pool and can't fully apply the strategy. Net effect: the solver's "one float per site" placeholder shapes the Monte Carlo float allocation, not the toggle.

**Suggested fix:** Have the solver emit ZERO floats by default and let A6 own the entire pool, OR have `computeSurplus` re-include solver-emitted floats when A6 is going to override.

### [INFO] `solver.ts:127-132`'s `takeMD()` / `takeCRNA()` round-robin pulls — no FTE weighting

**File:** `src/lib/gridCalculator/solver.ts:127-132`
**Category:** correctness
**Issue:** Both helpers walk the sorted-by-id pool sequentially. For a single-day grid this is fine, but the simulator hands the solver a synthetic 1.0-FTE roster, so this never surfaces a real issue. If/when the solver gets called with a real partial-FTE roster (e.g. for a directly-edited grid), the round-robin will under-assign partial-FTE providers because they're sorted alongside 1.0 FTE providers but consumed at the same rate.

**Suggested fix:** Document the FTE-unaware assumption explicitly, OR add a roster filter that pre-expands partial-FTE providers to their effective day-share before passing to the solver.

## What's good

- **Determinism contracts** are clearly stated in headers and enforced via stable sorts (`stableSiteCompare`, `stableProviderCompare`, sorted user-message payloads in `rulesNormalizer`). Repro-friendly from the start.
- **Universality discipline.** No `import` from FloorRunner-specific staffing-calculator modules anywhere in `src/lib/gridCalculator/`. Paoli references are confined to `seeds/paoli.ts` and to documentation comments — exactly what PRD §17's risk mitigation asks for.
- **Test seams.** Every module under `src/lib/gridCalculator/` has a sibling `__tests__/*.test.ts` with a tsx + node:assert harness (no vitest dependency required). The Anthropic stub pattern in `rulesNormalizer.test.ts` is reusable by `fteSimulator.test.ts` and is.
- **Migrations are idempotent.** Every CREATE TABLE / ADD COLUMN uses `IF NOT EXISTS`, every CHECK constraint is dropped-then-added, and the `NOTIFY pgrst, 'reload schema'` postscript matches FloorRunner's existing pattern. Re-runnable without coordination between sibling agents.
